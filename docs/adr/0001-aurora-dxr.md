# Validate HdAurora in an isolated Windows runtime

Use Autodesk Aurora v25.08-beta with its DXR backend for the Windows ray-tracing milestone. Autodesk pins its own OpenUSD 25.08 fork and oneTBB 2022.0.0, while the workstation's NVIDIA SDK uses TBB 2020.3. Build a separate runtime using the release's dependency versions so the current Storm environment stays usable and the initial test exercises a matched native stack. [Aurora release](https://github.com/Autodesk/Aurora/releases/tag/v25.08-beta) · [Versioned dependency installer](https://github.com/Autodesk/Aurora/blob/v25.08-beta/Scripts/installExternals.py)

## Local build and verification

The tag was checked out at `50eea04cc44c7b8c6bcfffdc68338755684bf3c8` in `%TEMP%\scenescout-aurora-v25.08`. The RTX 4070 Ti reported 12,282 MiB total VRAM and driver 621.24. The installed Visual Studio 2026 instance has a compiler executable but lacks the desktop C++ toolchain and Windows SDK needed for DXR. CMake 4.3 failed to configure with the Visual Studio 2026 generator. Autodesk lists Visual Studio 2022 and CMake 3.29.3 or later for this tag. [Versioned build instructions](https://github.com/Autodesk/Aurora/blob/v25.08-beta/Doc/Build.md)

After installing the desktop C++ components, CMake detected MSVC 19.44.35230 and Windows SDK 10.0.26100.0 using the Visual Studio 2026 generator with `-T v143`. Boost 1.88.0's bootstrap guessed an unknown toolset when Aurora passed `--prefix` before `vc143`. The scratch installer passes `vc143` first. For the OpenUSD build, enable MaterialX and use OpenGL for Storm and Hydra presentation.

The source audit found three points to verify once the build runs. The default DXR color and depth path copies through Hgi OpenGL into the bound Qt framebuffer. Check for horizontal padding at widths with unaligned D3D12 rows and verify that Hydra reports convergence for both buffers. Aurora advertises color and depth AOVs, so it lacks the prim ID AOV used by viewport picking. Failed device creation can also terminate the native process, so a plug-in registry check alone cannot verify the Storm fallback. [Render buffer](https://github.com/Autodesk/Aurora/blob/v25.08-beta/Libraries/HdAurora/HdAuroraRenderBuffer.cpp) · [Render pass](https://github.com/Autodesk/Aurora/blob/v25.08-beta/Libraries/HdAurora/HdAuroraRenderPass.cpp) · [Render delegate](https://github.com/Autodesk/Aurora/blob/v25.08-beta/Libraries/HdAurora/HdAuroraRenderDelegate.cpp)

The local D3D12 feature check reported DXR tier 1.2 on the RTX 4070 Ti. The existing Storm runtime rendered one Kitchen Set stage and then both Kitchen Set stages into separate 768×512 framebuffers. Pixel samples from the 70% wipe matched their respective full-stage images. The buffers showed distinct images before and after orbit. The 40 local SceneScout tests passed before renderer integration.

The local build uses Release x64 with the Visual Studio 2026 generator, v143, and Windows SDK 10.0.26100. Set `CMAKE_GENERATOR` and `CMAKE_GENERATOR_TOOLSET` in the build environment so OpenImageIO's nested dependencies also use v143. Use a short build directory and limit MSBuild and compiler workers. Install the pinned Imath 3.1.12 from the OpenEXR build into the OpenEXR prefix before building OpenImageIO. Use the SDK's underlying `PySide6/uic.exe` as `PYSIDEUICBINARY` for usdview. OpenUSD uses OpenGL presentation with MaterialX enabled, and Aurora uses DXR with Hgi ray tracing and denoising disabled.

The [native patch](../aurora-v25.08-beta.patch) keeps color and depth convergence in sync and removes D3D12 row padding before upload. It also adapts the Boost bootstrap and the Aurora C++ build to this toolchain. The project-local runtime keeps its MaterialX standard library beside `bin/aurora.dll` under `bin/MaterialX/libraries` as well as in the launcher’s USD library path.

The first 768×512 Aurora render showed one Kitchen Set stage and used approximately 303 MiB above the desktop GPU-memory baseline. The patched delegate rendered both Kitchen Set stages into separate 773×512 buffers. All 2,520 sampled wipe pixels matched the corresponding full-stage images. At 128 samples, the pair settled after 4.42 s from initial view setup and 0.25 s after orbit. Device-wide GPU memory peaked at 2,512 MiB, about 460 MiB above the pre-run baseline.

The full SceneScout window passed the renderer switch, mouse wipe, shared-camera orbit, Frame all, and return to Storm. The animated pump pair updated both Aurora images when the timeline jumped from time code 1 to 48. The sign-off fixture passed local payload unload and reload with Aurora active. The launcher selected `.aurora-runtime` from `scenescout.local.toml`. It kept Storm usable with a missing plug-in and with a registered plug-in whose DLL was missing. A viewport click after fallback picked a Stage A prim. All 40 local tests passed with the integration in place.

Aurora initialization runs in a separate probe process before the viewport switches renderers. The local runtime occupies approximately 0.87 GiB and uses its own native OpenUSD and Hydra binaries.
